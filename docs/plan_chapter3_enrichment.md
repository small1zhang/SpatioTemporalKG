## 二、文档中有价值但代码未覆盖（可引用的参考素材）

### 2.1 研究定位与动机分析（doc2 §1/§3）

doc2 提供了现有知识图谱的**三类核心不足**（静态性、层次割裂、检索方式固定），以及本文改进的定位。这些论述可以丰富第 3 章的引言部分：

> "现有交通知识图谱为离线批处理结构，难以表达同一地点在不同时段、天气下的规则约束变化"
> "已有工作多聚焦单一场景层或静态规则层，缺乏'场景事实—行为关系—规则判定'的跨层链路"

### 2.2 规则层与 GNN 的融合机制（doc2 §3.6）

doc2 提出规则层输出的**两种 GNN 落地形态**——作为节点特征拼接、作为注意力权重偏置——这在代码中未实现，但可写入第 3 章作为"前瞻性设计"。

以及 RSS "强先验" + GNN "统计建模"的互补定位。

### 2.3 形式化推理规则示例（doc1 §1.11.2 / §4.15）

doc1 对 **R1-R18 每条规则都给出了完整的形式化逻辑判别式**（如：

```prolog
YieldingToPedestrianViolation(A, P, t) ←
    VehicleEntity(A) ∧ PedestrianEntity(P) ∧
    is_on_crosswalk(P, t) ∧
    relative_distance(A, P, t) < 15m ∧
    speed(A, t) > 0.5 m/s
```

代码中只有 `check_Ri_*` 的实现函数，缺乏这种**逻辑式表达**，可以丰富论文的三线表。

### 2.4 详细的 CARLA API 字段映射表（doc1 §2.3 / §7.5）

doc1 为每个实体字段整理了"数据源/类型/单位/计算方法/可用性"五列映射表（如 VehicleEntity 18 个字段逐一标注）。代码文档中只有简单属性列表，论文中可以用这些表大幅丰富场景层描述。

### 2.5 场景-规则触发对照（doc1 §2.14 / §4.19）

doc1 给出 S00-S33 每个场景预期触发哪些规则（含对应 RSS 子类），这是一个完整的"验证矩阵"，论文中展示场景库设计时非常有用。

### 2.6 法规法条引用（doc2 §3.5）

doc2 的 R1-R18 每条都标注了具体法条来源（如"道交法第47条""实施条例第78条"）。代码中只有规则名称，论文中应加入这些法条依据提升可信度。

### 2.7 实验评估方法论（doc2 §7）

doc2 提出了完整的评估维度矩阵（构建准确性≥99%、更新效率 P95、增量一致性100%、垃圾延迟≤1帧等），为论文第6章实验设计提供了现成框架。

## 三、文档与代码的差异点（写论文时需注意）

### 3.1 RSS 参数不一致

| 参数 | 符号 | doc1 值 | 代码实际值 | 论文以代码为准 |
|------|------|---------|-----------|--------------|
| 反应时间 | ρ | 0.1 s | **0.3 s** | ✓ |
| 后车最大加速 | a_max_accel | 1.5 m/s² | **0.5 m/s²** | ✓ |
| 后车最小制动 | a_min_brake | 4.0 m/s² | **3.0 m/s²** | ✓ |
| 前车最大制动 | a_brake | 8.0 m/s² | **8.0 m/s²**（一致） |

### 3.2 行为防抖阈值不一致

| 关系类型 | doc1 阈值 | 代码阈值 |
|---------|----------|---------|
| standing_still | ≥10 帧 | **2 帧** |
| changing_lane | ≥5 帧 | **2 帧** |
| approaching | ≥2 帧 | **3 帧** |
| approaching_intersection | ≥3 帧 | **2 帧** |
| overtaking | — | **5 帧**（代码新增） |
| wrong_side_meeting | — | **1 帧**（代码新增，瞬时关系） |

### 3.3 属性字段差异

- doc1 提出 EnvironmentSnapshot 应有 `time_of_day_str` / `visibility_level` / `weather_severity` / `road_friction_estimated` 等派生属性 → **代码未实现**，这些字段目前为空
- doc1 提出 RoadElementEntity 有 `road_friction`（默认 0.7）→ **代码未实现**
- doc1 提出 `road_polygon` 作为 RoadElement 属性 → **代码未实现**
- doc1 使用 int 作为 actor_id 类型 → **代码使用 str**（如 "veh_123"）
- doc1 的 VehicleEntity 有 `bbox_center_x/y/z` → **代码只保留 `bbox_extent_x/y/z`**

### 3.4 生命周期管理模型差异

| 维度 | doc1 | 代码 |
|------|------|------|
| 状态 | 简单"进入/在场景/离开"三段 | 四状态 **CREATED→ACTIVE→STALE→INACTIVE** |
| Stale 机制 | 无 | 有（连续 N_stale 帧未出现→暂忘） |
| 过期处理 | 600 帧滑动窗口（doc2 §6.2） | 代码用 DefaultDebounceThreshold（无统一过期） |
| 版本化粒度 | 文档层概念 | 代码中有 `VersionManager` + `AttrVersion` |

### 3.5 增量引擎流程差异

| doc1 流程（5步） | 代码流程 |
|-----------------|---------|
| step1: 过期清理 | **无显式窗口 GC**（仅通过帧跳跃检测重置） |
| step2-4: 实体/属性/关系更新 | 对应代码的 diff→patch 步骤 |
| step5: 计算 RSS 并生成 SafetyEvent | 代码中 eval 步骤独立调用 RuleEnforcer |

### 3.6 场景库参数差异

- doc1 中 S10 预期触发 **R1+R13a**；代码中 S10 只预期 R1（R13a 代码中是 RSS 纵向，只有跟车场景才触发）
- doc1 中场景 6 帧/400ms；代码也是 6 帧/400ms → 一致

### 3.7 冲突/协调建议

| 差异项 | 论文处理建议 |
|-------|------------|
| RSS 参数 | **以代码值为准**（代码是实际运行值） |
| 防抖阈值 | **以代码值为准**（可在论文中添加注释：阈值经 CARLA 物理引擎标定调整） |
| 未实现的派生属性 | **不要写**，或标注为"预留设计" |
| 生命周期模型 | **以代码四状态为准**（比 doc 更完善） |
| doc2 的评估指标 | **可以作为实验章节框架**，但具体数值需以实测为准 |
| doc2 的规则层-GNN 融合 | 可作为"前瞻性讨论"写入第 3 章末尾或第 5 章 |

## 五、代码实现中值得写入论文但文档未覆盖的特色

1. **Ego-Centric 笛卡尔椭圆 ROI** + 按类别差异化半径（轿车 70m / 行人 40m / 自行车 50m）——这是代码阶段 1-6 的重头改动，doc 完全未提及
2. **五维重要性打分 E1-E5**（ego 权重 0.40 / 距离 0.20 / 可见性 0.15 / 交互 0.15 / 异常 0.10）
3. **边稀疏化 EdgePruner**（同类边按 importance top-k 保留）
4. **防抖状态机**的详细实现（on_counter/off_counter 双向阈值，比 doc 的简单计数器复杂得多）
5. **跨 chunk checkpoint 序列化**（IncrementalEngine + BehaviorRelationGenerator 均可 to_dict/load_dict）
6. **异常注入调度器**的 7 种异常类型 + 泊松过程调度
7. **coalesce_containment 图压缩模式**（长时运行用全局 scenario 节点替代逐帧 scenario_frame_F，边数降 95%+）
8. **数值属性防污染防御**（`_validate_numeric_attrs` 防御 `json.dumps(default=str)` 导致的字符串污染）
